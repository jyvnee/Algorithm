## 풀이 기록

### v1

#### 문제 정의

각 작업의 진도 `progresses`와 하루당 개발 속도 `speeds`가 주어진다. 진도가 100%가 되어야 배포할 수 있고, 앞선 작업이 아직 배포되지 않았다면 뒤에 있는 작업은 먼저 개발이 끝나도 대기했다가 앞선 작업과 함께 배포된다. 배포는 하루에 한 번만 이루어지며, 각 배포마다 몇 개의 작업이 함께 배포되는지를 순서대로 반환해야 한다.

#### 풀이 아이디어

작업은 큐처럼 앞에서부터 순서대로만 배포될 수 있으므로, 배열을 한 번 순회하면서 "현재 배포 그룹의 완료까지 남은 일수"를 기준으로 그룹을 나눈다.

1. 첫 번째 작업의 남은 일수를 `remaining`으로, 그 작업을 배포 그룹의 기준으로 삼고 `count = 1`로 시작한다.
2. 이후 작업을 순서대로 확인하며, 해당 작업의 남은 일수가 `remaining` 이하이면 같은 날 배포되므로 같은 그룹으로 묶어 `count`를 늘린다.
3. `remaining`보다 남은 일수가 더 크면 새로운 배포 그룹이 시작되는 지점이므로, 지금까지의 `count`를 결과에 추가하고 해당 작업을 새 기준(`remaining`)으로 삼아 `count`를 1로 초기화한다.
4. 배열의 마지막 작업까지 확인한 뒤, 마지막으로 진행 중이던 그룹의 `count`도 결과에 추가한다.

뒤에 있는 작업이 앞선 작업보다 먼저 개발을 마치더라도 앞선 작업의 배포일까지는 대기해야 하므로, 그룹의 기준이 되는 `remaining`은 그 그룹에서 가장 나중에 배포되는(=가장 먼저 등록된) 작업의 남은 일수로 고정된다.

#### 알고리즘 풀이

각 작업이 배포되기까지 남은 일수는 `(100 - progress)`를 `speed`로 나눈 값을 올림한 것과 같다. 실수 연산 없이 정수 연산만으로 올림을 구하기 위해 다음과 같이 계산한다.

```java
public int calculateRemain(int progress, int speed) {
    return (100 - progress + speed - 1) / speed;
}
```

`(100 - progress)`가 `speed`로 나누어떨어지지 않을 때 `speed - 1`을 더해주면 나눗셈에서 소수점이 항상 다음 정수로 올라가는 효과를 낸다.

메인 로직에서는 이 남은 일수를 기준으로 그룹을 나눈다.

```java
for (int i = 1; i < progresses.length; i++) {
    int taskRemaining = calculateRemain(progresses[i], speeds[i]);

    if (taskRemaining <= remaining) {
        count++;
    } else {
        list.add(count);
        count = 1;
        remaining = taskRemaining;
    }
}

list.add(count);
```

`taskRemaining <= remaining`은 현재 작업이 그룹 기준 작업보다 먼저(또는 같은 날) 개발이 끝난다는 뜻이므로 같은 배포 그룹에 포함시킨다. 반대로 `taskRemaining > remaining`이면 그룹 기준 작업이 이미 배포된 이후에나 완료되는 새 작업이므로 새로운 그룹을 시작한다.

마지막 그룹의 `count`는 반복문 안에서 특정 인덱스를 검사하는 대신, 반복문이 끝난 뒤 `list.add(count)`로 무조건 한 번 추가한다. 이렇게 하면 `progresses.length`가 1이어서 반복문이 한 번도 실행되지 않는 경우에도 초기값 `count = 1`이 그대로 결과에 추가되어 `[1]`을 올바르게 반환한다.

#### 시간복잡도

```text
O(N)
```

작업 개수 `N`에 대해 배열을 한 번만 순회하며, 각 반복에서 수행하는 연산은 상수 시간이다.

#### 공간복잡도

```text
O(N)
```

배포 그룹의 개수만큼 결과를 담는 `List<Integer>`와 최종 `answer` 배열이 필요하며, 최악의 경우(모든 작업이 각각 다른 날 배포되는 경우) 그룹의 개수가 `N`에 비례한다.

#### 개선 가능한 부분

- `List<Integer>`에 결과를 담았다가 `int[]`로 변환하는 대신, 최악의 경우 그룹 수가 `N`을 넘지 않는다는 점을 이용해 크기 `N`의 `int[]` 배열과 쓰기 인덱스를 사용하면 오토박싱 비용과 마지막 변환 루프를 없앨 수 있다.

#### 시행착오

- **문제:** 초기 구현에서는 마지막 그룹의 `count`를 반복문 안에서 `i == progresses.length - 1`일 때만 추가했다.
- **원인:** 반복문이 `i = 1`부터 시작하므로, `progresses.length`가 1이면 `i < progresses.length` 조건이 곧바로 거짓이 되어 반복문 자체가 실행되지 않았다. 그 결과 `count`가 한 번도 `list`에 추가되지 못해 빈 배열이 반환되었다.
- **해결:** 마지막 인덱스를 검사하는 조건을 반복문 안에서 제거하고, 반복문이 끝난 뒤 `list.add(count)`를 무조건 한 번 호출하도록 바꾸었다. 이렇게 하면 반복문이 실행되지 않는 경우에도 초기값 `count = 1`이 결과에 반영된다.
- **주의할 점:** 그룹화·누적 로직에서 "마지막 원소 처리"를 반복문 내부의 인덱스 조건으로 구현하면, 반복문이 아예 실행되지 않는 경계 입력(길이 1 등)에서 그 로직 자체가 누락될 수 있다. 가능하면 마지막 처리는 반복문 밖으로 빼서 입력 길이와 무관하게 항상 실행되도록 하는 편이 안전하다.
