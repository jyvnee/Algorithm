# 금과 은 운반하기

## 알고리즘 분류

- 이분 탐색
- 매개 변수 탐색
- 그리디

## 문제 정의

각 도시에 보유한 금과 은의 양, 트럭의 적재량, 편도 이동 시간이 주어진다. 한 번에 금과 은을 합쳐 적재량까지 운반할 수 있을 때, 필요한 금 `a`와 은 `b`를 새로운 도시로 모두 운반하는 데 필요한 최소 시간을 구한다.

## 풀이 기록

### v1

#### 풀이 아이디어

정답 시간을 직접 계산하기보다는, 특정 시간 `time` 안에 필요한 금과 은을 운반할 수 있는지를 판별한다.

- 어떤 시간 안에 운반이 가능하면, 그보다 더 긴 시간에도 항상 가능하다.
- 어떤 시간 안에 운반이 불가능하면, 그보다 짧은 시간에도 불가능하다.

따라서 `canMove(time)`의 결과가 `false`에서 `true`로 바뀌는 첫 시간을 이분 탐색으로 찾을 수 있다.

탐색 상한은 `400_000_000_000_000L`로 설정한다. 가장 느린 조건인 편도 시간 `100,000`, 적재량 `1`인 트럭 하나가 최대 `2,000,000,000`의 광물을 운반하는 경우도 포함할 수 있는 값이다.

#### 알고리즘 풀이

##### 1. 주어진 시간의 운반 횟수 계산

`i`번 도시의 트럭은 첫 번째 운반에 `t[i]`만큼 걸린다. 그 다음 운반부터는 돌아오는 시간까지 포함하여 `2 * t[i]`마다 한 번씩 운반한다.

따라서 `time` 안에 완료할 수 있는 운반 횟수는 다음과 같다.

```java
long moveCount = (time + t[i]) / (2L * t[i]);
```

이 식은 다음 계산을 한 줄로 표현한 것이다.

```text
time / (2 × t[i])
+ 나머지 시간이 t[i] 이상이면 1회
```

한 도시에서 운반할 수 있는 최대 광물의 양은 `moveCount * w[i]`이다. 다만 해당 도시가 실제로 보유한 양보다 많이 운반할 수는 없으므로 `Math.min`을 사용한다.

```java
long capacity = moveCount * w[i];

total += Math.min(g[i] + s[i], capacity);
gold += Math.min(g[i], capacity);
silver += Math.min(s[i], capacity);
```

##### 2. 가능 조건 판별

각 도시의 트럭은 금과 은을 섞어서 운반할 수 있다. 따라서 전체 적재 가능한 양만 검사하면 특정 광물이 부족한 경우를 구분할 수 없다. 다음 세 조건을 모두 만족해야 한다.

```text
운반 가능한 전체 광물의 합 >= a + b
운반 가능한 금의 합       >= a
운반 가능한 은의 합       >= b
```

- `total >= a + b`는 트럭의 전체 적재량이 충분한지 확인한다.
- `gold >= a`는 필요한 금을 채울 수 있는지 확인한다.
- `silver >= b`는 필요한 은을 채울 수 있는지 확인한다.

##### 3. 최소 시간 탐색

`canMove(mid)`가 `true`면 더 짧은 시간을 탐색하고, `false`면 `mid + 1`부터 더 긴 시간을 탐색한다.

현재 코드는 `left`와 `right`를 모두 정답 후보가 포함된 경계로 관리한다. 불가능한 `mid`는 정답이 될 수 없으므로 `left = mid + 1`로 제외하고, 가능한 `mid`는 최소 시간일 수 있으므로 `right = mid`로 남겨 둔다.

```java
while (left < right) {
    if (canMove(a, b, g, s, w, t, mid)) {
        right = mid;
    } else {
        left = mid + 1;
    }
    mid = left + (right - left) / 2;
}

return mid;
```

`left == right`가 되면 탐색을 종료한다. 매 반복의 끝에서 `mid`를 다시 계산하므로, 종료 시점에는 `left`, `right`, `mid`가 모두 최소 가능 시간을 가리킨다.

#### 시간복잡도

**O(N log T)**

- `N`은 도시의 수이다.
- `T`는 탐색 상한인 `400_000_000_000_000`이다.
- 한 번의 가능 여부 판별에서 모든 도시를 확인하므로 `O(N)`이 필요하다.
- 이분 탐색은 탐색 구간을 매번 절반으로 줄이므로 `O(log T)`번 수행한다.

```text
O(N) × O(log T)
→ O(N log T)
```

`T`가 고정된 상한이므로 실제 가능 여부 판별은 약 49번 수행된다.

#### 공간복잡도

**O(1)**

입력 배열 외에 전체 운반량, 금 운반량, 은 운반량 등 입력 크기와 관계없이 일정한 개수의 변수만 사용한다.

#### 개선 가능한 부분

- `mid`를 반복문 안에서 계산하고 종료 후 `left`를 반환하는 일반적인 형태로 바꾸면, `mid`가 최종 정답과 같은 이유를 따로 추적하지 않아도 되어 코드의 의도가 더 명확해진다.
- `totalTime`은 시간이 아니라 운반 횟수를 의미하므로 `moveCount` 또는 `deliveryCount`로 바꾸면 의도가 더 명확해진다.
- `totalTime * w[i]`를 `capacity`로 미리 계산하면 중복된 식을 줄일 수 있다.
- 가능 여부는 조건식을 바로 반환하면 더 간결하다.

  ```java
  return total >= (long) a + b && gold >= a && silver >= b;
  ```

- 이분 탐색과 모든 도시의 운반 가능량 확인이 모두 필요하므로, 점근적 시간복잡도 `O(N log T)`를 더 줄이기는 어렵다.

#### 시행착오

##### 1. 이분 탐색 상한에 `^` 사용

- **문제:** 초기 코드에서 `right = 10^10`으로 작성했다.
- **원인:** Java의 `^`는 제곱 연산자가 아니라 XOR 비트 연산자이다. `10 ^ 10`의 결과는 `0`이므로 탐색 구간이 처음부터 잘못 설정된다. 또한 `10,000,000,000`으로 의도했더라도 문제의 최대 정답을 포함하기에는 작다.
- **해결:** 제한 조건에서 최악의 경우를 계산해 `400_000_000_000_000L`로 설정했다.
- **주의할 점:** Java에서 거듭제곱이 필요하면 `Math.pow`를 사용하거나, 정수 상한은 정수 리터럴로 명시한다.

##### 2. 탐색 구간이 줄어들지 않음

- **문제:** 초기 코드는 가능하면 `right = mid`, 불가능하면 `left = mid`로 갱신했다. `mid`가 경계와 같아지면 구간이 더 이상 줄지 않는다.
- **해결:** 불가능한 `mid`는 다시 확인할 필요가 없으므로 `left = mid + 1`로 변경했다. 또한 반복 조건을 `left < right`로 변경하여 두 경계가 하나의 최소 가능 시간으로 만나면 탐색을 종료하도록 했다.
- **주의할 점:** 이분 탐색은 반복 조건과 경계 갱신 규칙을 하나의 패턴으로 일관되게 사용한다.

##### 3. 트럭의 왕복 시간을 반영하지 않음

- **문제:** 초기 코드는 `(time + t[i]) / t[i] * w[i]`로 운반량을 계산했다.
- **원인:** 첫 배달 후 다음 광물을 가져오려면 원래 도시로 돌아가야 하므로, 추가 배달에는 편도가 아닌 왕복 `2 * t[i]`가 필요하다.
- **해결:** `(time + t[i]) / (2 * t[i])`로 시간 안에 완료할 수 있는 운반 횟수를 계산했다.
- **주의할 점:** 반복 운반 문제에서는 첫 운반과 이후 운반의 소요 시간이 같은지 따로 확인한다.

##### 4. 전체 광물의 양만 확인

- **문제:** 초기 코드는 `total >= a + b`만으로 운반 가능 여부를 판별했다.
- **원인:** 전체 광물이 충분해도 필요한 금 또는 은이 부족할 수 있다. 예를 들어 은이 전혀 없고 금만 많은 경우, 전체 양 조건은 만족해도 은 요구량을 채울 수 없다.
- **해결:** `total`, `gold`, `silver`를 각각 계산하고 세 조건을 모두 확인하도록 변경했다.
- **주의할 점:** 서로 대체할 수 있는 자원이 하나의 용량을 공유하는 문제에서는, 전체 용량과 각 자원의 개별 요구량을 함께 검증한다.
